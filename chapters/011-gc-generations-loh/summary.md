# Summary — GC Generations & the Large Object Heap

**TL;DR:** Gen 0/Gen 1 allocation budgets aren't fixed constants — the GC recomputes each one after every collection from survival rate and collection cost, observable indirectly as `GC.GetGCMemoryInfo()`'s committed-bytes growing under allocation pressure and then plateauing once the segment is sized for the workload. A Gen 0 collection stays cheap even against a huge Gen 2 heap because of the **card table**: a JIT-inserted write barrier marks one byte dirty on any store that could create a cross-generational reference, so a Gen 0 collection only rescans dirty regions, never clean ones. Objects whose total size reaches **85,000 bytes** skip the generational heap entirely and land on the **Large Object Heap** — verified down to the exact byte in this chapter (`new byte[84_975]` is Gen 0, `new byte[84_976]` is already on the LOH). The LOH is swept but **not compacted by default**, because moving a huge object costs proportionally to its size; `GCSettings.LargeObjectHeapCompactionMode = CompactOnce` forces exactly one compacting pass and then resets itself. The Pinned Object Heap (.NET 5+) rounds out the picture — a home for long-held pinned allocations so they stop blocking compaction elsewhere.

**Key takeaways:**

- Gen 0/Gen 1 budgets are adaptive, recomputed after every collection from survival rate and collection cost — not a number you can read directly, but its consequence (committed heap size growing then plateauing) is observable via `GC.GetGCMemoryInfo()`.
- Modern .NET (since .NET 8) allocates heap space in fixed-size regions rather than one monolithic segment per generation — budget growth shows up as acquiring more regions, not extending one segment's boundary; the underlying budget/survival policy is unchanged.
- The card table and write barrier are why a Gen 0 collection doesn't need to rescan all of Gen 2 -- a write barrier dirties one card-table byte per cross-generational reference write, and a Gen 0 collection only checks dirty regions.
- The LOH threshold is 85,000 bytes of *total object size*, including the ~24-byte array header on a 64-bit runtime -- not element count, and easy to cross by one byte without noticing.
- The LOH is swept, not compacted, by default -- because a large object's compaction cost scales with its size. `GCSettings.LargeObjectHeapCompactionMode.CompactOnce` forces exactly one compacting collection, then resets to `Default`.
- LOH fragmentation is a real, measured failure mode that can cause an `OutOfMemoryException` even with plenty of total free memory -- the fix is pooling (`ArrayPool<T>`), a deliberate occasional `CompactOnce`, or both.
- The Pinned Object Heap (.NET 5+, `GC.AllocateArray<T>(pinned: true)`) exists so a long-held pinned allocation doesn't sit as an immovable obstacle inside a regular, otherwise-compactable segment.
