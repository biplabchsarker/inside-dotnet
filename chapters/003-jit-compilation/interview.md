# Interview Questions — JIT Compilation Explained

**Q1: What is the "prestub," and why does the CLR need one at all instead of just JIT-compiling everything when the assembly loads?**
A: The prestub is the initial, shared entry point every method table slot points at before that method has ever been compiled. It exists because .NET deliberately compiles methods *lazily* — compiling every method in an assembly at load time would pay JIT cost for code paths that might never execute. The prestub's job is narrow: detect "this method has never run," trigger compilation, and backpatch the method table slot (and already-resolved call sites) to point directly at the resulting native code. After that one redirect, the prestub is never touched again for that method.

**Q2: Explain tiered compilation to someone who only knows "the JIT compiles IL to native code." What problem does each tier solve?**
A: Tier 0 solves the startup-latency problem: it's a fast, minimally-optimized compile so a method can start running as soon as possible, and it instruments the method with call-count tracking as a side effect. Tier 1 solves the throughput problem: once a method's call count shows it's actually hot, the runtime recompiles it with full optimizations on a background thread and swaps the entry point over — without ever blocking the calling threads on that recompilation. Splitting the concern into two tiers means the vast majority of rarely-called methods never pay optimization cost at all, while genuinely hot methods still get fully optimized code, automatically, with no developer intervention.

**Q3: What is On-Stack Replacement, and what gap in tiered compilation does it close?**
A: Without OSR, a method already executing a long-running loop in Tier 0 would keep running that unoptimized loop to completion even after its call count crossed the Tier 1 threshold, because promotion normally only takes effect on the *next* call, not the current one. OSR allows a currently-executing method to transition to optimized code mid-execution, inside that same call, so a single long-running loop doesn't get stuck on Tier 0 performance for its entire duration just because it started before promotion happened.

**Q4: How does ReadyToRun interact with tiered compilation — are they competing mechanisms or complementary ones?**
A: Complementary. R2R answers "where does the *first* native code for this method come from" — a precompiled, versioned cache instead of a fresh JIT invocation, used only if it matches the running CLR exactly, with a transparent JIT fallback if it doesn't. Tiered compilation answers a separate question — "should this method's code get replaced with something more optimized over time" — and applies regardless of whether the starting point was R2R or a fresh Tier 0 JIT compile. An R2R'd method can absolutely still get promoted to Tier 1 if it's hot.

**Q5: A colleague says "we should just use Native AOT for everything, it's strictly faster." How do you respond?**
A: Push back on "strictly." Native AOT genuinely wins on cold-start latency and memory footprint by removing the JIT step and trimming unreachable code — real advantages for CLI tools, scale-to-zero containers, or latency-billed functions. But it requires ahead-of-time knowledge of everything that will run: heavy reflection, `Reflection.Emit`-based dynamic codegen, and some plugin-loading patterns either don't work or need explicit rework/annotations, because there's no JIT fallback at run time to compile something that wasn't statically discovered. It also means publishing a separate binary per target OS/architecture instead of one portable IL artifact. It's the right tool for specific deployment shapes, not a universal upgrade.
