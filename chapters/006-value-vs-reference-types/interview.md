# Interview Questions — Value Types vs Reference Types

**Q1: What's actually copied when you assign one variable to another — and does it depend on where the variable is stored?**
A: It depends on the *type*, not the storage location. Assigning a value type copies its field data (a `memcpy` of however many bytes the struct occupies). Assigning a reference type copies the reference itself — a single pointer-sized value — so both variables end up referring to the same underlying object. This holds regardless of whether that value type happens to live on the stack, inside a heap object's field, or inside an array element.

**Q2: Are value types always allocated on the stack?**
A: No — that's an oversimplification worth correcting precisely in an interview. A value type is stored wherever its *containing context* is stored: a local variable's value typically lives in a stack frame; a value type that's a field of a class lives inside that class instance, wherever that instance is (almost always the heap); a value type that's an array element lives inside the array's storage, and arrays are themselves heap objects. A value type only gets its own independent heap allocation when it's boxed.

**Q3: Why are mutable structs considered dangerous, and what's the concrete failure mode?**
A: Because most access paths to a struct other than the original variable — a property getter, a `foreach` iteration variable, certain indexer patterns — hand you back a *copy*, and mutating that copy is either a compile error (the safe outcome, e.g. mutating a `List<T>` element through its indexer directly) or a silent no-op that changes nothing observable (the dangerous outcome, e.g. `foreach (var p in points) p.X = 5;`, which compiles cleanly and does nothing useful because `p` is a fresh copy discarded each iteration). The fix is defaulting mutable value types to `readonly struct` so the mistake fails to compile instead of failing silently at run time.

**Q4: Is it true that structs are always faster than classes?**
A: No, and treating it as an absolute is a red flag in a design review. Structs avoid heap allocation and GC pressure when they're small, short-lived, and not boxed — a genuine win in that regime. But every assignment, method call, and return copies the struct's full field data; a large struct copied repeatedly through several call layers can accumulate more `memcpy` cost than a class's one-time allocation plus cheap pointer copies everywhere else. The right choice is a function of struct size, copy frequency, and mutability needs — not a blanket rule.

**Q5: What's the difference between `readonly struct` and `ref struct`, and why does `Span<T>` need to be the latter?**
A: `readonly struct` is a correctness/optimization contract — every instance field is immutable, which lets the compiler elide defensive copies it would otherwise insert before calling members through `in` parameters or `readonly` fields. `ref struct` is a placement contract enforced by the runtime — instances can never be boxed, stored as a field of an ordinary class, captured by a lambda or async state machine, or used as a generic type argument; they must stay on the stack. `Span<T>` requires `ref struct` because it can wrap a reference into stack-allocated or pinned memory; if an instance could escape to the heap and outlive the memory it references, dereferencing it later would read invalid memory with no GC tracking to prevent or even detect it.

**Q6: How does default equality differ between a custom `struct` and a custom `class`, and what's the performance implication?**
A: A `struct` without an `Equals` override falls back to `ValueType.Equals`, which uses reflection to compare fields one by one (with a bitwise fast path when there are no reference-type fields). A `class` without an override falls back to `object.Equals`, which is pure reference equality — same object, not same data. The performance implication is one-directional: reflection-based struct equality is measurably slower than a hand-written or `record struct`-generated comparison, so structs destined for hash-based collections or frequent equality checks should override `Equals`/`GetHashCode` explicitly even though the default is already correct.
